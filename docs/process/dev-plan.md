# 実装の計画（2026-11-07 夜）

今夜、エージェントに実装を任せるための計画です。何を作るかは企画書が正本で、この文書は順番と完了の条件だけを決めます。企画書と食い違ったら企画書に従います。

## ゴール

**一通りの UI ができていて、使える状態**にする。具体的には、次の流れを 3 人で最後まで通せることです。

旅を作る → 招待 URL で 3 人が入る → それぞれ希望を書く → ピンが立つ → 建築して模型が建つ → ルート案とスケジュールが出る → 全員が投票してルートが決まる → しおりを見る → 決まったあとに 1 か所足して組み直される

見た目の作り込みより、この流れが途切れずに動くことを優先します。

## Gemini

Cloud の Gemini（Vertex AI）はまだ使いません。呼び出し口を 1 つにまとめ、`GEMINI_PROVIDER` で切り替えます。

| 値 | 使う場面 | 中身 |
| --- | --- | --- |
| `stub`（既定） | 普段の開発、CI、本番 | 固定の応答。流れの確認用 |
| `agy` | ローカルで本物の Gemini を試すとき | Functions Emulator から `agy` を子プロセスで呼ぶ。Flash は `gemini-3.8-flash-*`（つないである。1 日の上限 `AGY_MAX_CALLS`、既定 30）、Argon は `gemini-4-argon-*`（つないである。1 日の上限 `AGY_MAX_ARGON_CALLS`、既定 20。Flash とは別に数える） |
| `vertex` | 使わない | 回数の上限と費用の確認が済むまで無効 |

- 今の `USE_REAL_GEMINI`（`true` で Vertex を呼ぶ）は、この `GEMINI_PROVIDER` に置き換える
- `agy` は開発者の Antigravity アカウントのクォータで動き、1 回 20〜40 秒かかります。agy が入っていない環境では `stub` に戻します
- `agy` の応答は JSON として検証し、形が違えば 1 回だけやり直し、だめなら `stub` に戻します
- 呼び出し口の型（入力と出力）は、`stub` と `agy` で同じにします。後で `vertex` を足しても画面側を変えずに済むようにするためです

## 地図

- 地図は案 A（Google Maps に模型を重ねる）に決定済みです
- キーは `VITE_GOOGLE_MAPS_API_KEY`、マップ ID は `VITE_GOOGLE_MAPS_MAP_ID` で渡します。設定方法は `docs/process/setup.md`
- 課金を避けるため、1 日の上限をかけてあります。地図の読み込み 300 回、Places のテキスト検索と詳細取得が各 30 回、Routes が 30 回です。写真、オートコンプリート、周辺検索、3D 地図、距離行列は 0 回で、使えません（開発を始めたときの数。Places はそのあと上げたので、今の上限は `docs/process/setup.md` の「課金を避ける上限」）
- キーはブラウザ用で、Functions からは使えません。Places で実在を確かめる処理は今夜は作らず、Gemini の提案した場所をそのまま使います
- Maps 由来の内容を 3D 生成の入力にしない、自作地図と Maps API を一緒に使わない（`CLAUDE.md`）

## 複数人シミュレーション

テストとデモ動画の両方に使います。

- 開発用の画面を 1 つ作り、スマホ幅の画面を 3 つ横に並べる。3 つは別々の匿名ユーザーとして動く（同じオリジンでも別のユーザーになるよう、Firebase のアプリ名と保存先を分ける）
- 3 人の操作は台本で進める。台本は「A が旅を作る、B と C が入る、それぞれ希望を書く……」と企画書の流れに沿わせる
- 同じ台本を、画面なしでも Emulator に対して流せるようにし、最後の状態を確かめるテストにする
- この画面は Emulator のときだけ開けるようにし、本番では出さない

実装（段 7、`web/src/pages/dev-sim/`）：開発サーバー（`npm run dev` の http://localhost:5173 ）で `/dev/sim` を開く。viewport は 1280×900。本物のアプリの iframe を 3 つ並べ（iframe の name で別の匿名ユーザーにする。`web/src/shared/lib/simFrame.ts`）、台本は `config/scenario.json`。画面なしの同じ台本は `scripts/sim-headless.mjs`（`npm run verify` が流す）。既定は 3 画面とも地図なしで、`/dev/sim?map=on` で左の 1 画面だけ本物の地図になる。本番のビルドには、この画面も台本も入らない（`import.meta.env.DEV` の中だけ）

## 決まっていないことの扱い

途中で止まらないよう、次は仮の案で進めます。仮の案は企画書の「議論済み」の目印より下に書き、朝にチームで確かめます。

| 決まっていないこと | 仮の案 |
| --- | --- |
| 決まったあとの組み直しで、今のルートに近い形を保てないとき | 組み直したルートを採用し、全員に通知する |
| 匿名ログインでの旅の一覧 | 自分が members にいる旅を集める。端末が変わると一覧も変わることを画面に書く |
| 見た目の案のどれにするか | A＋C（A のぷっくりと、C のマップが主役を合わせたもの）で作る。`screenshots/` の全画面と `design-options/` の A＋C の説明（縁と厚みのあるボタン、落ち着いた地図、緑＝進む・探す、オレンジ＝建てる、青＝ルート、マークにできるものはマーク、地図の印はピン、M PLUS Rounded 1c）に合わせる。色、角丸、フォント、影は CSS 変数にまとめ、案が変わっても差し替えられるようにする |
| 投票で票が割れたとき | 票の多い案に決める。同数なら、先に提案された案（案 A、B、C の順）にする |
| スケジュールの形 | 日ごとに、時刻、場所、滞在時間、次への移動を並べる |

これ以外で迷ったら、企画書の目的（全員が主人公、幹事に集中させない）に近い方を選び、プルリクエストの説明に書きます。
