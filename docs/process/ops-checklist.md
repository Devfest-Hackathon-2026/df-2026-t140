# 運用の点検表

AI に任せる仕組みが安全に動いているかを見る 6 つの観点です。自分たちが Claude Code などを使うときの設定の点検表にもなります。安全装置（トレース、停止条件）は機能より先に作りました。

| 観点 | このリポジトリでしていること | 残っている穴 |
| --- | --- | --- |
| トレース | ガードの判断（止めた・確認した・通した）と、層のチェックの指摘を `.harness/trace/<日付>.jsonl` に残す（手元だけ）。会話の全文は各ツールの記録（Claude Code は transcript_path）にある。CI の結果は GitHub に残る | 手元の記録は人ごとにばらばら。集めるなら `npm run trace` の結果を持ち寄る |
| 停止条件 | 下の表の 3 段。Stop のフックは一度だけ止めて知らせ、二度目は止めない | 長時間の自動実行の上限は、実行する人が決める |
| ガードレール | 4 つの層（[README.md](README.md)）。危険な命令、main での作業、デプロイと deploy ブランチへの反映、有料 API、.env（命令、リダイレクト、Read と Grep の道具）、ガードレールの書き換え | main にブランチ保護がない。deploy のブランチ保護（push を人に限る）は人の作業で、かけるまでは層 1 だけが AI を止める。node -e で fs を使うなど、ツールの外で動かす迂回は層 2〜3 でしか止まらない（.env の値を読むことは、どの層でも完全には止められない） |
| 評価 | 決まった処理はテスト（`npm run test:harness`：ガードの正常系と異常系、層のチェック、git hooks を一時リポジトリで実際に動かす）。LLM の判断は評価セット（`npm run eval:review`） | 評価セットは小さい。見逃しや誤った指摘が見つかったら、その PR を元にケースを足す |
| 費用 | Cloud の Gemini を本物にする設定、有料 API の直接の呼び出し、Cloud の上限や課金の変更、手元からのデプロイを止める。本番へのデプロイは人が deploy ブランチへ反映したときだけ。文書だけの変更では CI の重い確認を走らせない。レビュー役の評価は 1 件ごとに費用の上限を付ける | Maps の 1 日の上限と予算アラートは Cloud 側の設定（人） |
| 人の確認 | PR の承認と、費用・方針・.env・権限の判断は人。AI の merge は、会話で人と合意した作業で、先頭の commit の手元の確認の記録があり、別のコンテキストのレビュー役が承認した PR（記録と承認はガードが確かめる。CI は条件にしない。人の merge 指示は待たない）。ガードレールの書き換えは人に確認を求める。人の判断は `todo/humans/` に集め、決まったら done と理由 | レビューの目印は AI が書けるので、手順を飛ばさないための確認にとどまる。夜中の作業は朝にまとめて確かめる（下記） |

## 停止条件

上限の大きさは「無応答 < 内側 < 外側」の順にします。内側が先に止まれば、外側の上限まで無駄に動き続けません。

| 段 | 何が止める | 上限 | 場所 |
| --- | --- | --- | --- |
| 無応答 | ハーネスが呼ぶ外部の命令（git fetch、gh） | ネットワーク 6 秒、手元 10 秒。push（pre-push のフックを待つ）は 60 秒 | `scripts/harness/lib/proc.mjs`、`scripts/harness/work.mjs`、`scripts/harness/lib/publish-humans.mjs` |
| 内側（ツール 1 回） | フックの上限 | 命令の前 20 秒、セッションの始め 30 秒、編集の後と終わり 15 秒 | `.claude/settings.json`、`.codex/hooks.json` など |
| 内側（ツール 1 回） | AI ツールの命令の上限 | Claude Code の Bash は既定 2 分 | 各ツール |
| 外側（エージェント全体） | レビュー役の手数 | 40 手 | `.claude/agents/reviewer.md` |
| 外側（エージェント全体） | 終わる前の確認 | Stop のフックは 1 回だけ止める（ループしない） | `scripts/harness/hook.mjs` |
| 外側（エージェント全体） | 自動実行（`claude -p`）の手数と費用 | 実行する人が決める（例：`--max-turns 150 --max-budget-usd 10`） | 実行の命令 |

フックが落ちたときや上限を過ぎたとき、Claude Code、Codex、Gemini CLI は止めずに通します（fail-open）。後ろの git hooks と CI が同じことを確かめるためです。Antigravity は逆に、フックが落ちると操作を止めます（fail-closed）。そのためアダプターは、中でエラーが起きても必ず「通す」を返してから終わります。

## 夜中に AI に任せるとき

- 自動実行には手数と費用の上限を付ける（上の表）
- 作業ごとに作業宣言と PR を作らせる（ガードが main での作業を止めるので、そうなる）
- 朝に人がすること：`npm run work -- status` で進み具合を見る、`npm run human -- list` で判断待ちを片付ける、`npm run trace` で何が止められたかを見る、夜のあいだに merge された PR を見直す

## 失敗したとき

AI に直させる前に、原因がどこにあるかを先に切り分けます。

1. 要件：作業宣言の目的や完了条件があいまいだった → 宣言を直す
2. 設計：設計方針が足りない、または合わない → design-principles.md を直す（例外が繰り返し出るのは、方針を見直す合図）
3. 実装：コードの誤り → 直す

ガードやチェックが関わる失敗は、トレースで「LLM の判断」（危ない命令を出そうとした、指示を読み違えた）か「ツールの実装」（ガードの止めすぎ・見逃し）かを分けます。ツールの実装なら、`scripts/harness/tests/cases/` にその入力を足してから直します。

## プロンプトと文書の見直し

プロンプトもコードと同じように膨らみます。

- CLAUDE.md は 150 行、AGENTS.md と GEMINI.md は 60 行までにしてある（CI が数える）。超えたら、詳しいことを docs/ の目的別の文書に移し、CLAUDE.md には道案内だけを残す
- 新しいサブエージェント、skill、MCP は、測った結果「足りない」と分かってから足す。今あるサブエージェントはレビュー役の 1 つだけ（実装とは別のコンテキストが要るため）
- 区切り（1 日の終わりなど）に、トレースで多く止められたルールと、例外の一覧（`npm run check:harness`）を見て、方針か手順を直すか決める
