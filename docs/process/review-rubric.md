# PR の評価軸

PR を merge してよいかを測る基準です。人のレビューも AI のレビューもこれを使います。完了条件は評価の基準でもあるので、「動いた」ではなく「作業宣言の完了条件を満たしたか」で測ります。

機械で見る部分（決まった処理）と、判断で見る部分（LLM と人）を分けています。機械で見る部分は CI の「Harness」とレビューパック（`npm run review-pack`）に結果が出るので、レビュー役は判断し直さず、結果を確かめて該当する項目に結びつけるだけにします。

## 項目

| ID | 項目 | 機械で見ること | 判断で見ること | 重い指摘の例 |
| --- | --- | --- | --- | --- |
| R1 | 完了条件 | 作業宣言があり、完了条件に印があるか | 各完了条件を、コードと証拠（テスト、確認テストの結果、動画）で本当に満たしているか | 完了条件を満たした証拠がない |
| R2 | 正本との一致 | — | 企画書・画面・技術構成と合っているか。何を作るかが変わるなら、先に企画書を直したか（`spec/proposal-first`） | 企画書でやめた案（ルートを自分で引くなど）を、企画書を直さずに実装している |
| R3 | 失格・規約 | 他社 AI の SDK、秘密情報、置いてはいけないファイル | Maps 由来の内容を 3D 生成の入力にしていないか（Firestore を通した受け渡しも）、自作地図と Maps API の併用、Google 技術が中心か、PoC の流用、デモの偽装 | Places の説明文を模型の生成に渡している |
| R4 | 設計 | 層のチェック（`docs/architecture/design-principles.md` の machine のルール） | judgement のルール（`ui/render-only`、`fn/idempotent`、`fn/lazy-init`）。スライスの分け方と名前、公開の入口に出すもの | トリガーが 2 回来ると二重に書き込む。ui の中で投票を集計している |
| R5 | 例外 | `@harness-exception` の形（理由があるか、ID が正しいか） | 理由が妥当か、代替案を本当に検討したか、解消条件があるか、ほかの方法で避けられないか | 「時間がないため」だけで、方針から外れている |
| R6 | 正しさ | — | 不具合、境界の値、エラーと空の状態、非同期の競合（購読の後片付け、StrictMode）、web と functions の型のずれ、スマホでの表示 | 購読を止めずに画面を離れ、書き込みが二重になる |
| R7 | 安全と費用 | — | Security Rules で本人とメンバーに限っているか。Gemini の呼び出しがログイン確認と回数の上限を通るか（`cost/gemini-guarded`）。Maps の上限を超える使い方をしていないか | 誰でも呼べる関数から Gemini を呼んでいる |
| R8 | 検証 | CI（verify、Harness）の結果 | 変えた振る舞いをテストか確認テストで押さえたか。画面が変わるなら動きを見せる証拠があるか | 新しい Security Rules に確認テストがない |
| R9 | 宣言と範囲 | 宣言した scope の外の変更、ブランチ名 | 範囲の外の変更に理由があるか。PR が大きすぎないか。関係のない変更が混ざっていないか | 宣言にない共有ファイルを大きく書き換えている |
| R10 | 記録と人の判断 | 人の判断（todo/humans/）の書き方、足した依存の出典 | 技術の選定を decisions.md に書いたか（人が決めたものとして）。費用・方針・.env・権限の判断を AI が勝手にしていないか。AI の使いどころを ai-usage.md に残したか | 人が決めるはずの有料 API の利用を、AI が決めて実装している |

## 重さ

| 重さ | 意味 | merge |
| --- | --- | --- |
| blocker | 失格、事故、データの破壊、費用の暴走、完了条件の未達 | 直すまで不可 |
| major | 不具合や設計の崩れ。後から直すと高くつく | 直すか、理由を PR に書いて人が判断 |
| minor | 直したほうがよいが、後でもよい | 可 |
| nit | 好みや細かい書き方 | 可 |

## 結論の出し方

- `REQUEST_CHANGES`：blocker か major が 1 つでもある
- `APPROVE`：blocker も major もない（AI は GitHub の承認はせず、コメントで結論を書く。この結論の目印がレビューした commit に付き、会話で人と合意した作業なら、AI が merge できる）
- `COMMENT`：判断に必要な情報が足りない（何が足りないかを書く）

## 指摘の書き方

- 1 つの指摘に、項目の ID、重さ、ファイルと行、何が起きるか（入力と結果）、直し方を書く
- 証拠のない指摘はしない。PR の説明（実装した側の主張）はうのみにせず、コードで確かめる
- 機械のチェックが通っていることは指摘しない。機械で見られないことに時間を使う
